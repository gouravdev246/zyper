# Product Requirements Document (PRD)
# Personal AI Operator
**Document status:** Draft v1.0  
**Date:** 21 October 2026  
**Product type:** Personal AI assistant with desktop control and cloud integrations  
**Primary user:** Single personal user  
**Target platform:** Windows desktop + web services  
**Primary languages:** TypeScript and Python

---

## 1. Executive Summary

### 1.1 Product Overview

Personal AI Operator is a personal artificial intelligence system that can understand natural-language requests, plan multi-step tasks, interact with authorized online services, control selected Windows desktop capabilities, and remember useful context across conversations.

Unlike a traditional conversational assistant, the system is designed to complete tasks rather than only explain how to complete them.

Examples include reading and summarizing emails, drafting replies, managing approved X (Twitter) activities, searching the web, opening desktop applications, searching permitted local files, controlling music playback, and coordinating several of these actions in one workflow.

The system combines an AI reasoning and orchestration layer, reusable integrations, a local Windows companion, persistent workflow execution, and a rule-based permission engine.

The core principle is:

**The AI determines what work should be done. The application determines what is permitted. Authorized tools perform the actual work.**

### 1.2 Problem Statement

Current productivity workflows often require users to switch between separate applications and repeatedly perform the same operations.

A user may need to:
- Read multiple emails and identify important messages.
- Prepare replies and send them after review.
- Research a topic across websites.
- Open a code editor and organize project files.
- Check upcoming calendar events.
- Start a coding playlist.
- Review outstanding tasks and prepare a daily briefing.

These actions are individually straightforward but become tedious when repeated across applications.

The Personal AI Operator aims to provide a unified interface that coordinates these activities through natural language, chat, voice, and scheduled automation.

### 1.3 Product Vision

Build a trusted personal AI operator that can understand goals, use connected tools, execute approved workflows, recover from interruptions, and report verifiable results.

The long-term vision includes:
- Cross-application task execution.
- Persistent conversational and project context.
- Rule-based proactive assistance.
- Desktop and browser interaction.
- Voice-driven operation.
- Extensible tools and specialist agents.
- Transparent permissions and action history.

### 1.4 Target User

The initial product is for one or two person using a Windows laptop for development, communication, research, productivity, and everyday computing.

The architecture should support additional users in the future, but multi-tenant functionality is not required for the first release.

## 2. Product Goals and Non-Goals

### 2.1 Goals

1. Provide a unified desktop interface for chat, voice, tasks, and approvals.
2. Connect authorized external services using their existing APIs.
3. Execute multi-step workflows through a persistent orchestration engine.
4. Support rule-based autonomous execution for explicitly approved routine actions.
5. Control selected local Windows applications through a restricted companion.
6. Maintain useful context between conversations and workflow executions.
7. Make task progress, permissions, failures, and outcomes visible.
8. Minimize custom implementations by reusing mature frameworks, SDKs, and existing tools.
9. Provide reliable cancellation, retry, recovery, and audit functionality.
10. Allow new integrations to be added without rewriting the core system.

### 2.2 Non-Goals for the MVP

The first release will not attempt to:
- Replace Windows or operate as a full operating system.
- Control every application or website.
- Execute arbitrary shell commands generated by an LLM.
- Run unrestricted autonomous financial transactions.
- Bypass provider authentication, API limits, or access controls.
- Support multiple users, teams, or enterprise administration.
- Train a proprietary foundation model.
- Build a custom speech recognition or synthesis model.
- Build a new browser automation engine.
- Implement a complex multi-agent society where agents communicate without limits.
- Guarantee that every task can be completed without human intervention.

These capabilities can be reconsidered after the core workflows are reliable.

## 3. Product Principles

### 3.1 Reuse Before Reinventing

Before implementing a feature, determine whether a maintained library, provider API, or existing framework already solves the problem.

Preferred examples:
- Electron for desktop packaging and system integration.
- React for the interface.
- LangGraph for stateful AI workflows and resumable execution.
- Provider SDKs for LLM calls.
- Official APIs for Gmail, Calendar, and X.
- Playwright for browser automation.
- Windows UI Automation for native application interaction.
- Prisma for database access and migrations.
- Existing OAuth libraries for authorization flows.
- Established voice APIs for speech recognition, speech synthesis, or realtime audio.

Custom code should focus on product-specific orchestration, policies, interfaces, and integration glue.

### 3.2 Least Privilege

Each integration receives only the scopes required for its enabled features.

A connected account does not automatically grant unrestricted permission to perform every operation supported by that provider.

### 3.3 Human-Controlled Autonomy

The user explicitly configures which routine actions may execute automatically.

Consequential actions require approval unless a narrow, explicit automation rule permits them.

### 3.4 Observable Execution

Every workflow must expose its status, task history, pending approvals, errors, and final outcome.

### 3.5 Graceful Failure

A failed integration must not cause the system to claim that a task succeeded.

The system should preserve completed work, report partial results, and allow safe resumption where possible.

## 4. Core User Stories

### US-01: Chat with the assistant

As a user, I want to describe a task in natural language so that the assistant can understand my goal and suggest or execute appropriate actions.

**Acceptance criteria**
- The user can create and continue conversations.
- Conversation history persists across application restarts.
- The assistant streams responses where supported.
- The user can cancel an active run.
- Failed requests produce a useful error rather than a false success message.

### US-02: Read and summarize email

As a user, I want the assistant to inspect authorized emails and identify important messages.

**Acceptance criteria**
- Gmail can be connected using OAuth.
- The assistant can retrieve permitted messages.
- Summaries reference the relevant messages.
- Email content is treated as untrusted input.
- Reading emails does not require send permission.

### US-03: Draft and send email

As a user, I want the assistant to prepare replies and send them only when authorized.

**Acceptance criteria**
- The assistant can create a draft.
- The user can inspect and edit the recipient, subject, and body.
- Sending requires an explicit approval or an applicable approved automation rule.
- The approval is bound to the exact action payload.
- The execution result is recorded.

### US-04: Manage X activities

As a user, I want to research topics, draft posts, and manage supported X actions.

**Acceptance criteria**
- The user connects an authorized account.
- The system checks available API capabilities and account permissions.
- Posts can be drafted and reviewed.
- Publishing requires approval by default.
- Unsupported operations are reported clearly.

### US-05: Control Windows applications

As a user, I want to ask the assistant to open selected applications and control basic desktop functions.

**Acceptance criteria**
- The companion is paired with the user's account.
- Only registered actions are executable.
- Supported applications can be opened by their configured identifiers.
- Basic media operations can be invoked.
- Every local action produces a structured result.
- Revoking the device disables remote command execution.

### US-06: Search local files

As a user, I want the assistant to search selected folders without giving it unrestricted access to my entire computer.

**Acceptance criteria**
- The user explicitly selects approved folders.
- The search tool accepts approved folder identifiers rather than arbitrary filesystem paths.
- File content is accessed only when the relevant permission exists.
- File results are displayed with their locations.
- Directory traversal outside approved roots is blocked.

### US-07: Use voice

As a user, I want to speak to the assistant and receive spoken responses.

**Acceptance criteria**
- Push-to-talk is available.
- The microphone state is visible.
- Voice input follows the same authorization rules as text input.
- The user can interrupt or cancel supported voice interactions.
- Sensitive actions are presented for clear confirmation.

### US-08: Configure routine automation

As a user, I want to configure recurring tasks that run under specific conditions.

**Acceptance criteria**
- The user can create, inspect, disable, and delete rules.
- Each rule defines its trigger, conditions, allowed actions, and limits.
- The system records each execution.
- Failed jobs do not silently repeat unsafe side effects.
- A global pause control prevents new automated actions.

## 5. Functional Requirements

### FR-01: Desktop Interface

The application shall provide:
- Chat interface.
- Conversation history.
- Voice controls.
- Active task indicator.
- Workflow and task detail panels.
- Pending approval queue.
- Connected services page.
- Automation rules page.
- Memory and privacy settings.
- Action history and logs.
- Global pause and cancellation controls.

### FR-02: Task Planning

The planner shall:
1. Receive the user's goal and relevant context.
2. Identify required tasks.
3. Determine dependencies.
4. Select registered tools and specialist agents.
5. Estimate whether the task requires approval.
6. Generate a structured task plan.
7. Validate the plan before execution.

The planner must not grant itself new permissions or invent tool capabilities.

### FR-03: Workflow Execution

The orchestration system shall support:
- Sequential execution.
- Bounded parallel execution.
- Dependency-aware scheduling.
- Conditional branches.
- Tool execution.
- Human approval pauses.
- Retry policies.
- Cancellation.
- Persistent checkpoints.
- Partial completion.
- Final synthesis.

### FR-04: Tool Registry

Every tool shall declare:
- Unique tool identifier.
- Human-readable description.
- Version.
- Input schema.
- Output schema.
- Required integration.
- Required permissions.
- Side-effect classification.
- Timeout.
- Retry policy.
- Idempotency behavior.
- Execution adapter.

Only registered tools may be called.

### FR-05: Authorization and Approval

The policy engine shall:
- Check user and device identity.
- Verify connected accounts.
- Check granted OAuth scopes.
- Evaluate the user's configured permissions.
- Determine whether approval is required.
- Validate approval expiry and action payload.
- Recheck permissions before execution.
- Record the decision and result.

### FR-06: Persistence

The system shall persist:
- Conversations and messages.
- Runs and task states.
- Task dependencies.
- Agent outputs and revisions.
- Approval requests.
- Tool execution results.
- Automation rules.
- Connected integrations.
- Device registrations.
- Audit events.
- Relevant user preferences.

### FR-07: Notifications and Proactive Tasks

The system shall support scheduled jobs and event-triggered workflows where the provider supports the required integration.

Examples:
- Daily briefing.
- Scheduled inbox summary.
- Calendar reminders.
- Follow-up on an unfinished workflow.
- Notifications when a configured task fails.

Notifications and recurring checks must be configurable and revocable.

## 6. Recommended Technology Stack

Use a TypeScript monorepo for the application and a Python service for AI orchestration.

### 6.1 Desktop Application

**Electron + React + TypeScript**

Recommended supporting tools:
- Vite for renderer development and bundling.
- Electron's main/preload/renderer process architecture.
- React Router for navigation if needed.
- TanStack Query for server state.
- A maintained UI component library such as shadcn/ui.
- Zod for client-side form validation.
- A maintained Markdown renderer for assistant responses.

Electron must be configured with context isolation, renderer sandboxing, Node integration disabled in the renderer, and a restrictive Content Security Policy.

Official reference: https://www.electronjs.org/docs/latest/tutorial/security/

### 6.2 Backend API

**Node.js + Express + TypeScript**

Responsibilities:
- Public API.
- Authentication and sessions.
- Input validation.
- Authorization checks.
- Integration management.
- Run creation.
- Approval handling.
- Audit logging.
- Event streaming.
- Communication with internal services.

Recommended reusable libraries:
- Zod for request and response validation.
- Prisma Client for database access.
- Pino for structured logging.
- OpenTelemetry SDKs for tracing.
- An established authentication library or identity provider appropriate to the deployment.

### 6.3 AI Orchestration

**Python + FastAPI + LangGraph**

Responsibilities:
- Planning.
- Agent workflow execution.
- Task dependencies.
- Conditional routing.
- Bounded parallel execution.
- Reviewer workflows.
- Checkpointing and resumable execution.
- Final synthesis.

Recommended reusable libraries:
- LangGraph for workflow graphs, state persistence, and human-in-the-loop execution.
- Provider SDKs for model interaction.
- Pydantic for request and state validation.
- HTTPX for asynchronous internal API calls.
- Pytest for tests.

Official references:
- https://docs.langchain.com/oss/python/langgraph/overview
- https://docs.langchain.com/oss/python/langgraph/persistence
- https://docs.langchain.com/oss/python/langgraph/interrupts

### 6.4 Database and Background Work

**PostgreSQL + Prisma**

Use PostgreSQL for durable application state.

Use a PostgreSQL-backed LangGraph checkpointer for workflow checkpoints where supported by the chosen version and deployment.

**Redis + BullMQ** may be used for Node.js background jobs such as scheduled checks and notification delivery.

Avoid introducing two competing systems of record for workflow state. The orchestration engine owns its graph state; the application database owns product records and authorization.

Official references:
- https://www.prisma.io/docs
- https://docs.bullmq.io/guide/introduction

### 6.5 Browser and Desktop Automation

**Playwright with TypeScript** for supported browser workflows.

Official reference: https://playwright.dev/docs/

For native Windows UI interaction, prefer the Windows UI Automation framework or a maintained automation library that wraps it.

Official reference: https://learn.microsoft.com/en-us/windows/win32/winauto/uiauto-uiautomationoverview

Use screenshot-driven computer interaction only where API or semantic UI automation is insufficient.

### 6.6 Voice

Begin with push-to-talk and existing speech services:
- Speech-to-text.
- Text-to-speech.
- Optional realtime speech API.

Do not build custom speech recognition or synthesis models.

The voice interface must call the same backend task and authorization APIs as the text interface.

### 6.7 Testing and Developer Tooling

Use:
- Vitest for TypeScript unit tests.
- Pytest for Python tests.
- Playwright Test for end-to-end UI tests.
- Docker Compose for local PostgreSQL and Redis.
- GitHub Actions or an equivalent CI system.
- ESLint and Prettier.
- Ruff and a Python type checker.
- Dependency and secret scanning.

Pin dependency versions and use lockfiles.

## 7. Architecture

### 7.1 Logical Architecture

The system consists of six primary layers.

**Layer 1: User Interface**
- Electron desktop application.
- React renderer.
- Chat, voice, approvals, settings, and activity views.

**Layer 2: Application API**
- Express.
- Authentication.
- User and device authorization.
- Run lifecycle.
- Integration connections.
- Approval management.

**Layer 3: Orchestration**
- Python FastAPI service.
- LangGraph workflow.
- Planner, task scheduler, specialist agents, reviewer, and synthesizer.

**Layer 4: Policy and Tool Execution**
- Tool registry.
- Policy engine.
- OAuth-aware connectors.
- Approval service.
- Local device command service.

**Layer 5: Local Windows Companion**
- Device pairing.
- Restricted local tool registry.
- Application launching.
- Approved-folder search.
- Browser automation.
- Media controls.
- Native UI automation.

**Layer 6: Persistence and Observability**
- PostgreSQL.
- Redis if required.
- Workflow checkpoints.
- Audit events.
- Structured logs and traces.

### 7.2 Request Lifecycle

1. The user submits text or voice input.
2. The desktop sends the request to the authenticated API.
3. The API creates a persistent run.
4. The planner creates a structured task plan.
5. The scheduler determines which tasks are ready.
6. Eligible tasks execute through registered tool adapters.
7. The policy engine blocks unauthorized operations and creates approval requests when required.
8. Approved workflows resume from persisted state.
9. Outputs are validated and stored.
10. The synthesizer creates the final response.
11. The API streams progress and results to the desktop.

### 7.3 Failure Handling

The architecture must handle:
- Model timeouts.
- Provider rate limits.
- Expired OAuth tokens.
- Revoked permissions.
- Device disconnections.
- Duplicate events.
- Failed tool calls.
- Workflow restarts.
- User cancellation.
- Approval expiry.
- Partial completion.

Retries must be bounded and operation-specific. A timeout during a side effect does not necessarily mean the side effect failed; check provider state before attempting it again.

## 8. Agent Design

### 8.1 Planner

The planner converts a user goal into a validated workflow.

It identifies:
- Goal.
- Tasks.
- Task dependencies.
- Required tools.
- Expected outputs.
- Approval checkpoints.
- Budget and time limits.

The planner may propose tasks but cannot authorize actions.

### 8.2 Executor

The executor:
- Finds tasks whose dependencies are satisfied.
- Applies concurrency limits.
- Dispatches tasks to tool adapters.
- Stores results.
- Retries eligible failures.
- Updates task status.

### 8.3 Specialist Agents

Initial specialists:
- Research agent.
- Communication agent.
- Productivity agent.
- Desktop agent.
- Reviewer.
- Final synthesizer.

Specialists should be modules in the same orchestration service initially. They do not all need separate model instances.

### 8.4 Reviewer

The reviewer checks:
- Whether the result addresses the user's request.
- Whether evidence supports factual claims.
- Whether required fields are missing.
- Whether tasks contradict one another.
- Whether the final response accurately describes completed actions.

Review rounds must be bounded.

### 8.5 Dynamic Planning

The first release should use an initial task plan with limited replanning.

If research reveals an important missing requirement, the planner may create an additional task. It must not create unlimited tasks or exceed the run budget.

## 9. Data Model

Use PostgreSQL as the authoritative data store.

Required tables:

1. `users`
2. `devices`
3. `conversations`
4. `messages`
5. `runs`
6. `tasks`
7. `task_dependencies`
8. `agent_outputs`
9. `tool_connections`
10. `oauth_credentials`
11. `tool_permissions`
12. `automation_rules`
13. `action_approvals`
14. `action_executions`
15. `memories`
16. `audit_events`
17. `scheduled_jobs`

### 9.1 Core Relationships

- A user owns conversations, devices, connections, rules, and runs.
- A conversation contains messages.
- A run contains tasks.
- Tasks can depend on other tasks in the same run.
- Tasks can have multiple versioned outputs.
- Tool connections belong to a user.
- Permissions belong to a user and a registered tool or operation.
- Approvals refer to a specific proposed action.
- Executions record actual side effects.
- Audit events record security-sensitive state changes.

### 9.2 Data Rules

- Use UUID identifiers.
- Use foreign keys.
- Index frequently queried status and timestamp fields.
- Validate JSONB against versioned schemas.
- Prevent dependency cycles.
- Use idempotency keys for side effects.
- Encrypt credentials separately from ordinary task data.
- Apply retention policies to checkpoints, logs, and messages.
- Ensure that user-owned records cannot be accessed through another user's identifiers.
- Preserve approval and execution history separately.

### 9.3 Long-Term Memory

Long-term memory is optional for the initial MVP.

Start with explicit preferences and project facts stored as structured records. Add semantic retrieval only when a real use case requires searching a larger collection of historical information.

Each memory should have:
- Content.
- Category.
- Source.
- Creation timestamp.
- Optional expiry.
- User visibility and deletion controls.

Do not automatically store every email, file, or conversation as permanent memory.

## 10. OAuth and Integration Requirements

### 10.1 OAuth Architecture

The backend should manage OAuth authorization and token storage for cloud integrations.

The flow must include:
1. User initiates a connection.
2. Backend creates an authorization request.
3. User is redirected to the provider.
4. User grants requested scopes.
5. Provider returns an authorization code.
6. Backend validates state and exchanges the code.
7. Tokens are stored securely.
8. The connection is tested.
9. The user can inspect and revoke the connection.

Use established OAuth libraries rather than implementing the protocol manually.

Google reference: https://developers.google.com/identity/protocols/oauth2/web-server

### 10.2 Gmail

Initial features:
- List unread messages.
- Read permitted messages.
- Retrieve message metadata.
- Summarize messages.
- Create drafts.

Later features:
- Send approved replies.
- Label or organize messages where supported.
- Configure inbox summaries.

Use official Gmail API endpoints and the minimum necessary OAuth scopes.

Official reference: https://developers.google.com/workspace/gmail/api

### 10.3 Google Calendar

Initial features:
- List upcoming events.
- Summarize the day's schedule.
- Prepare daily briefings.

Later features:
- Create and update events.
- Add reminders.
- Propose schedule changes.

Use the official Calendar API and request write scopes only when needed.

### 10.4 X

Initial features:
- Connect an authorized account.
- Research topics.
- Draft post content.
- Display account information permitted by the API.

Later features:
- Publish approved posts.
- Retrieve supported engagement metrics.
- Manage other operations exposed by the current API plan.

Verify current API access, pricing, rate limits, and available endpoints before implementation.

### 10.5 OAuth Security

- Request scopes incrementally.
- Encrypt refresh tokens.
- Never expose provider tokens to the LLM.
- Handle revocation and expiration.
- Prevent tokens from appearing in logs.
- Validate callback state.
- Restrict redirect URIs.
- Disconnecting an account must disable its tools.
- Recheck granted scopes before every sensitive operation.

## 11. Tool Registry and Permission Engine

### 11.1 Tool Contract

Each tool must define:
- Name.
- Description.
- Version.
- Input schema.
- Output schema.
- Required scopes.
- Permission category.
- Execution adapter.
- Timeout.
- Retry policy.
- Idempotency requirements.

### 11.2 Initial Tools

**Cloud tools**
- `gmail.list_unread`
- `gmail.read_message`
- `gmail.create_draft`
- `gmail.send`
- `calendar.list_events`
- `web.search`
- `x.create_post`

**Local tools**
- `app.open`
- `files.search`
- `media.control`
- `browser.navigate`
- `browser.extract_content`
- `desktop.inspect_ui`
- `desktop.perform_approved_action`

Only implement tools whose provider capabilities, security requirements, and required permissions have been verified.

### 11.3 Permission Categories

**Read-only:** May run automatically when the user has granted the relevant permission.

**Preparatory:** May create drafts or reports according to configured rules.

**Consequential:** Sending messages, publishing posts, deleting files, making purchases, and other significant side effects require approval by default.

### 11.4 Approval Requirements

Each approval must:
- Identify the proposed operation.
- Show relevant arguments.
- Identify the target account or device.
- Include an expiry.
- Be bound to the action payload.
- Record the user's decision.
- Be checked again immediately before execution.

Any material change to the approved action requires a new approval.

## 12. Windows Local Companion

### 12.1 Responsibilities

The companion provides restricted local capabilities that cloud APIs cannot provide.

Initial capabilities:
- Launch approved applications.
- Search explicitly approved folders.
- Control basic media playback.
- Open approved browser destinations.
- Return structured execution results.

Later capabilities:
- Inspect accessible Windows UI elements.
- Interact with native application controls.
- Perform bounded workflows across multiple applications.

### 12.2 Device Pairing

The companion must:
1. Request pairing from the desktop application.
2. Receive a short-lived pairing code.
3. Authenticate the pairing request.
4. Register a device identity.
5. Establish an authenticated outbound connection.
6. Accept only authorized commands.
7. Support credential revocation.

Do not expose an unrestricted remote-control endpoint on the user's laptop.

### 12.3 Local Execution

Every action must pass local validation.

For example, file search should use an approved folder identifier mapped to a known directory. It must not accept arbitrary paths generated by the model.

The local tool registry must reject:
- Unknown tool names.
- Invalid arguments.
- Expired commands.
- Revoked device sessions.
- Unauthorized directories.
- Unsupported application identifiers.

### 12.4 Desktop Automation Strategy

Prefer:
1. Official application APIs.
2. Native operating-system capabilities.
3. Playwright for browser automation.
4. Windows UI Automation for accessible native controls.
5. Screenshot-driven computer interaction as a fallback.

Use existing frameworks and libraries wherever possible.

### 12.5 Local Security

- Run without administrator privileges.
- Avoid unrestricted shell execution.
- Restrict filesystem access.
- Validate URLs and application identifiers.
- Enforce action timeouts.
- Log sensitive operations.
- Stop accepting commands when the device is revoked.
- Require local confirmation for sensitive or ambiguous operations.

## 13. API Specification

### 13.1 Public API

Use versioned routes under `/api/v1`.

| Method | Endpoint | Purpose |
|---|---|---|
| POST | `/runs` | Create a workflow |
| GET | `/runs/:id` | Retrieve run status |
| POST | `/runs/:id/cancel` | Cancel a run |
| GET | `/runs/:id/events` | Stream workflow events |
| GET | `/approvals` | List pending approvals |
| POST | `/approvals/:id/decision` | Approve or reject |
| GET | `/connections` | List integrations |
| POST | `/connections/:provider/connect` | Start OAuth |
| DELETE | `/connections/:id` | Disconnect integration |
| GET | `/automation-rules` | List automation rules |
| POST | `/automation-rules` | Create a rule |
| PATCH | `/automation-rules/:id` | Update or disable a rule |
| GET | `/devices` | List paired devices |
| POST | `/devices/pair` | Start pairing |
| DELETE | `/devices/:id` | Revoke a device |
| GET | `/audit-events` | Retrieve action history |

### 13.2 Internal Orchestration API

Keep the Python service private.

Suggested endpoints:
- `POST /internal/v1/runs`
- `GET /internal/v1/runs/{id}`
- `POST /internal/v1/runs/{id}/resume`
- `POST /internal/v1/runs/{id}/cancel`
- `GET /internal/v1/health`

Use authenticated service-to-service communication.

### 13.3 Event Types

The frontend should support events such as:
- `run.created`
- `run.started`
- `task.started`
- `task.completed`
- `task.failed`
- `approval.required`
- `approval.approved`
- `approval.rejected`
- `device.connected`
- `device.disconnected`
- `run.completed`
- `run.cancelled`

Events must include identifiers and timestamps. Persist important events before publishing them so that reconnection does not lose the authoritative execution history.

## 16. Security and Privacy Requirements

### 16.1 Application Security

- Authenticate every public API request.
- Authorize every user-owned resource.
- Validate all inputs.
- Restrict CORS.
- Use secure transport.
- Apply rate limits.
- Protect secrets.
- Keep dependencies updated.
- Use restrictive Electron security settings.
- Validate all IPC messages.
- Restrict external navigation.

### 16.2 Prompt Injection

Email bodies, web pages, documents, and other retrieved content must be treated as untrusted data.

Instructions embedded in retrieved content cannot change tool permissions, approve actions, or override system policies.

The policy engine must remain outside the LLM's control.

### 16.3 Credential Protection

- Store OAuth credentials encrypted.
- Use a managed key service in production.
- Restrict access to credential decryption.
- Avoid logging tokens.
- Rotate or revoke compromised credentials.
- Keep development secrets out of source control.

### 16.4 Auditability

Record:
- Who initiated a run.
- Which tools were proposed.
- Which permissions were evaluated.
- Whether approval was required.
- Who approved or rejected.
- What action was executed.
- Whether execution succeeded.
- Which errors occurred.

Audit records should not unnecessarily contain full message bodies, tokens, or other sensitive content.

### 16.5 Emergency Controls

Provide:
- Global pause.
- Per-integration disconnect.
- Per-device revocation.
- Per-rule disable.
- Run cancellation.
- Credential revocation guidance.

A pause operation should prevent new side effects. It cannot guarantee reversal of an action that has already completed.

## 20. Risks and Mitigations

| Risk | Mitigation |
|---|---|
| LLM produces incorrect plans | Structured output validation and bounded workflows |
| Prompt injection | Treat external content as untrusted; enforce deterministic policy |
| Excessive model cost | Budgets, model routing, bounded parallelism |
| Desktop automation is unreliable | Prefer APIs and semantic UI automation |
| OAuth complexity | Use official SDKs and incremental scopes |
| Duplicate side effects | Idempotency, provider reconciliation, execution records |
| Workflow failures | Persistent checkpoints and recovery tests |
| Integration API changes | Versioned adapters and provider contract tests |
| Excessive feature scope | Deliver one end-to-end workflow before expanding |
| Sensitive data exposure | Least privilege, encryption, redaction, retention controls |

## 23. Final Product Definition

Personal AI Operator is a Windows desktop and cloud-backed AI application that combines natural-language interaction, voice, stateful task orchestration, reusable cloud integrations, and restricted local computer control.

Its defining feature is not simply that it can answer questions or call tools. It can coordinate multi-step tasks across authorized services, remember useful context, pause for approval, recover from failures, and report what it actually accomplished.

The product will be developed incrementally, reusing established frameworks and APIs rather than rebuilding existing infrastructure. All consequential actions will remain subject to explicit permissions, and the application will maintain a durable record of its decisions and execution results.

**Primary success criterion:** A user can describe a real task in natural language and trust the operator to complete the authorized portions, ask for approval when required, recover safely from failures, and clearly explain the outcome.
